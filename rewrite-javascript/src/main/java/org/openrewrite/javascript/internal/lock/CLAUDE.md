# Node lock regeneration

Each package manager's lock is regenerated by a Java port of that package manager's own code. No package manager
runs. The design and its rules are in `doc/adr/0013-lock-regeneration-follows-each-package-manager.md`; this file
is how the ports are written and tested.

| Package | Ports |
|---|---|
| `npm` | `@npmcli/arborist` and its libraries, npm 11.17.0 |
| `bun` | Bun 1.3.10 |
| `yarnclassic` | Yarn 1.22.22 |
| `berry` | Yarn 4.10.3; every 4.x release runs as it, with its own data and lockfile version |
| `pnpm` | pnpm 11.2.2; releases from 11.0.6 to below 12 run as it (`Main.RUNS_AS_PORTED`) |
| this package | what the ports share: JavaScript and Node behavior, never resolution |

`NativeLockEngine` builds a package manager's inputs from the request and calls its `Port`. A result is the lock the
package manager writes, byte for byte, or a failure of a `LockFileRegeneration.Kind`.

## Porting

- One class per upstream module, named after it, with its control flow, names and iteration order. The class
  Javadoc names the file and release: "Port of @npmcli/arborist lib/arborist/build-ideal-tree.js (npm 11.17.0)".
- JavaScript semantics come from `EcmaScript` (each port's `Js` extends it), `EventLoop`, `V8Date`, `V8RegExp`,
  `V8Sort`, `WhatwgUrl`, `PosixPath`, `LocaleCompare`. Never substitute Java's equivalent: `Number()`, property
  order, sort stability, UTF-16 comparison and promise ordering all reach the lock.
- A library several package managers use is ported once here, with its release as an option (`Minimatch`, `Ssri`,
  `Ini`, `JsYaml`, `Picomatch`, ...). node-semver is `NodeSemver` in `org.openrewrite.javascript.semver`, outside
  rewrite-core's `org.openrewrite.semver`, which the host shares with every recipe jar.
- The package manager decides. When its source does not settle a question, record it before porting. An unported
  part of the package manager is a work item, never a failure.
- A failure says what the engine cannot know or what the package manager rejects, with the package manager's own
  message. The written lock must survive a second install (`LockOnlyInstall.verify`).

## Testing

- **Module tests:** each ported module runs its upstream test cases. A library's cases are rows captured from its
  own test suite at each release (`src/test/resources/.../lock/upstream/`, written by `generate/upstream-calls.js`).
  Node built-ins are compared with rows from Node 24.19.0 (`generate/node-builtins.js`).
- **Round trips:** `<Pm>LockRoundTripTest` installs over every recorded lock with nothing changed, and expects the
  lock's own bytes, or what the package manager was recorded rewriting it to.
- **Scenarios:** `<Pm>ScenarioTest` replays every scenario offline and expects `after` byte for byte, or the
  recorded `expect` line (`Expect`).
- **Recipes:** `*Dependency*Test`, `*LockRegenTest` and `*CatalogTest` in `org.openrewrite.javascript` run the
  recipes over the same scenarios.

```bash
./gradlew :rewrite-javascript:test --tests 'org.openrewrite.javascript.internal.lock*'
```

## Scenarios

Scenarios live in openrewrite/rewrite-javascript-lock-fixtures as `lock/<family>/<scenario>/`
(<https://github.com/openrewrite/rewrite-javascript-lock-fixtures>). The build downloads its `main` into
`build/lock-fixtures` once; delete that directory to pick up newer fixtures. `REWRITE_LOCK_SCENARIOS` adds another
directory of scenarios to the scenario tests, and `REWRITE_LOCK_HTTP_CACHE` adds registry responses they fall back
on.

To add one, record it with the fixtures repository's `record/` scripts (its README says which). Push it to that
repository's `main`, delete `build/lock-fixtures`, and run the tests. Never hand-edit a recorded lock, and change
a test's expectation only when a recording says so.

## A new package-manager release

Diff the upstream source between the ported tag and the new one, limited to the modules the port's classes name.
Port the differences, update the release in each class's Javadoc, then re-record the scenarios with the new release.
A scenario whose lock changes is the new release's behavior, kept as recorded.
