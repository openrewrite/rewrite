## ChangeDependencyGroupIdAndArtifactId: change POMs that have no Maven model

`ChangeDependencyGroupIdAndArtifactId`, like every `MavenVisitor`, only visits a `pom.xml` that carries a Maven model. A module whose parent or dependencies could not be resolved when the LST was built has none. In a multi-module build, the parent's `<dependencyManagement>` entry is then renamed while the module keeps the old coordinates without a version, and Maven rejects the build.

- POMs without a model are now changed by their literal coordinates: dependencies, managed dependencies, plugin dependencies and annotation processor paths, plus the sibling exclusion.
- A declared version, literal or a property, is replaced with the new one. A missing version is added only with `overrideManagedVersion` or `changeManagedDependency: false`.
- `pom.xml` files under `src/main`, `src/test` and `src/it` are left alone.
- A first commit extracts the version selection and sibling exclusion that both visitors share.

Not covered: the new coordinates managed only by a remote parent or BOM, which needs the missing model.

---

Context: the Spring Framework 4.x migration recipes carry a workaround recipe for this today (Jackson 1, ROME, Velocity and similar coordinate moves). Tested with the unit tests, and with a snapshot of this branch loaded by the Moderne CLI from a recipe jar, on a local two-module repository whose module only Maven itself could resolve: the released recipe renamed only the parent's managed dependency, this branch renamed the module's dependency too. A base-versus-branch run of four Spring-era dependency moves on two real Maven repositories, whose POMs all have a model, gave identical patches.
