## Recipes for a checked exception that a library stops declaring

When a new library version stops declaring a checked exception, two kinds of code stop compiling: an override that still declares it, and a `catch` of it around calls that no longer throw it. Recipes run on code built against the old version, where the method types still declare the exception, so both have to be found by method pattern. `RemoveMethodThrows` removes the exception unconditionally, and no recipe removes such a `catch`.

- `RemoveMethodThrows` gets an optional `keepIfThrownByBody`: the exception stays where the body can still throw it (a `throw`, another call declaring it or a supertype, a resource's `close()`, a call without types).
- New `RemoveCatchOfExceptionNoLongerThrown(methodPattern, exceptionType)` removes the `catch`, or the multi-catch alternative, where only matching calls can throw the exception, and unwraps a `try` left bare.

Not covered: `keepIfThrownByBody` on Kotlin `@Throws`.

---

Context: the Spring Framework 4.x migration needs both (EhCache factory bean overrides, `JsonPathExpectationsHelper` catches) and carries workaround recipes for them today. Tested with the unit tests, and with snapshots loaded by the Moderne CLI on real repositories: `RemoveMethodThrows` with and without the option gave identical patches where the body does not throw, and the new recipe, run as a stress test on `DateFormat.parse` catches, rewrote 12 files of a large application without errors or unreachable code.
